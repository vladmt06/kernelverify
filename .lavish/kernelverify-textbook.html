The problem we exist to solve

A kernel is a small program that runs on a graphics chip (a GPU). When you run an AI model on your Mac, almost all of the work is a handful of kernels executing over and over: multiply this matrix, normalise these numbers, pick these experts. The model is the data; the kernels are the machinery that moves it.

Kernels are hard to write and easy to get subtly wrong. A kernel can produce numbers that are close enough to look fine, pass the test that ships alongside it, and still be wrong in a way that quietly degrades the model's output. This is documented, not hypothetical: a research paper (The Correctness Illusion in LLM-Generated GPU Kernels) collected real kernels written by AI that passed their own benchmarks while being incorrect. We use that collection as ground truth.

The core insight, and the thing everything else follows from: whether a bug escapes is not a property of the bug. It is a property of the pair - the bug and the specific test you happened to run. The same bug is invisible under one test and obvious under another.

We measured this on the published corpus rather than asserting it. Running the standard check that ships with these kernels: 2 of 10 known-buggy kernels passed as if correct, and across all cases roughly a quarter of tests failed to see a fault that was really there. That measurement is frozen in the repository - any change we make must still reproduce it exactly, so we can never accidentally flatter ourselves later.

So the product question became: if escape depends on which tests you run, which set of tests catches the most bugs for a fixed amount of testing? That is a question you can answer with evidence, and nobody in this ecosystem had answered it.

The four pieces, in plain terms

PieceWhat it actually is
Seam A switch inside our correct kernel that turns on one specific bug. One kernel, many switches, so a broken version is guaranteed to differ from the correct one in exactly one known way.
Fault catalogue The list of every bug we can produce - currently 65. Ten of them are copies of the real published bugs, which is what proves our synthetic list is not self-serving.
Test policy A strategy for choosing which inputs to test with, given a fixed budget of tests. Policies are never allowed to know which bugs exist - they may only look at the shape of the operation. That rule is what makes the comparison honest.
Budget (B) How many test runs each policy is allowed per operation. Comparing policies at equal budget is the only fair comparison; anyone can win by testing more.

What we test across

A test is not just "some numbers". We found that the pattern of the input matters more than its size, and we test along three axes:

Shape and precision

How big the data is, and whether numbers are stored with more or fewer digits of accuracy.

Scale

Whether the values are large or tiny. Some bugs only appear when a small safety constant starts to dominate.

Structure

Deliberately awkward patterns: all values identical, opposing signs, near-zero. This axis exists because of a measured failure - see below.

Why the third axis exists. One real production bug (an attention kernel mishandling a fully-masked row) scored 0% detectable under ordinary random inputs at any size. Random numbers never produce the structure it needs. We added structured input patterns and it became catchable. We did not guess this; the measurement forced it.

The hard part: how do you know what "wrong" is?

This is the deepest idea in the project, and the one worth understanding properly, because everything we sell rests on it.

Computers do not do exact arithmetic on decimals. They round. So if two people write the same calculation correctly but add the numbers up in a different order, they get slightly different answers - both correct. That means you cannot check a kernel by asking "does it match the reference exactly?" It never will.

The naive fix is to allow a fixed margin of error: "close enough is fine." That fails in both directions, and we measured both failures:

Margin too tight

A provably correct kernel gets flagged as broken, because the input was awkward enough that legitimate rounding exceeded the margin. A verifier that cries wolf is worthless.

Margin too loose

Real bugs slip through. We measured one industry gate that admits 18 of 40 of our faults - it is a published, shipping quality check.

Our answer: measure the margin instead of choosing it

For every single test case, we compute the margin fresh, like this: 

flowchart LR
  A["This exact test case"] --> B["Run several DIFFERENT
but provably correct
implementations"]
  B --> C["How far apart do
they land?
(the 'floor')"]
  C --> D["Margin = floor x safety factor K"]
  D --> E{"Kernel differs
by more than that?"}
  E -->|yes| F["Genuinely wrong"]
  E -->|no| G["Within legitimate
disagreement"]

If correct implementations already disagree by this much on this input, a kernel differing by that much has not proven itself wrong. If it differs by much more, it has.

The safety factor K is calibrated, not chosen: K = 1.5 for ordinary arithmetic, K = 3 for compressed-weight arithmetic. Each was derived by measuring what the honest implementations actually demand, then checked against implementations held back from the calibration.

The rule that came out of this the hard way: every legitimately-different style of implementation needs at least two representatives in that comparison group. With only one, removing it removes the whole style, and the calibration measures the absence rather than the spread. This error inflated one safety factor from 2.27 to 7.02 before we caught it. It is now a permanent rule in the project's instructions.

Compressed weights change what "correct" even means

To run a large model on a laptop, its numbers are compressed (this is called quantization - storing each number in 4 bits instead of 16). A kernel that reads compressed weights should not be judged against the original uncompressed model: it can never match that. It must be judged against the compressed weights it was actually given. Getting this right required reverse-engineering Apple's compression routine exactly, bit for bit, from its source. Without that, every compressed kernel would look broken.

"Directional" means: reproduced across multiple interleaved runs, but not yet certified on a quiet machine. Correctness carries no such caveat - it reproduces anywhere and is pinned by tests.

Result 4: measuring speed is harder than it looks

Three separate failures taught us this, and all three are now permanent rules:

  • The same fixed piece of work measured 131.7 then 93.1 microseconds minutes apart, because the GPU changes speed depending on load. A comparison run in two separate passes reversed sign completely - a "win" was really a loss.
  • Interleaving the two things being compared fixes that, but cannot detect it. So we also reject any result whose repeat measurements disagree with each other. On its first run that rule auto-rejected exactly the results a person had already withheld by hand.
  • The interference is not other people's software - it is your own open apps. Terminal alone was measured competing at 30% CPU.

Result 5: we found a hole in our own verifier, and closed it

A kernel that violates our own rules (holding intermediate arithmetic at low precision) was passing our checks in one specific configuration. Rather than hide it, we measured exactly where the boundary is:

Kernel styleCaught by testing?How the rule is enforced
Naive (adds up left to right) Yes - 192 of 280 cases, up to 23x over tolerance Numerically, by the battery
Optimised (adds up in a tree) No - 0 of 280 cases, provably invisible By reading the kernel's source in the certificate

This is the honest result: the style an AI would most likely write is caught by testing; the style that cannot be caught by any test is caught by inspection instead. Both are stated in the public document, deliberately.

The product, and how it is supposed to make money

The positioning is verified first, fast second. The documented pain in this ecosystem is silent wrongness - software that ships broken kernels while its benchmarks look fine - and no competitor occupies "verified" on Apple hardware.

Given away free

The kernel pack itself, open source. It is the credibility artifact and the demand probe. Open licensing is also what makes each certificate re-checkable by anyone.

Sold

Continuous certification for companies shipping their own kernels; private per-chip verified packs and early access; support agreements.

The three 90-day gates

Each is written to be falsifiable, so the project can be proven wrong rather than drifting:

  • Gate 1 - speed to market
    One verified kernel released within a week of a major model launch, against a community that takes weeks to months.
  • Gate 2 - does anyone care
    Findings published by day 21; then a merged or seriously-reviewed contribution, or 3+ inbound responses, or one vendor conversation.
  • Gate 3 - is it actually faster
    A verified 15%+ improvement on real hardware. Below that, the speed story is dropped and verification stands alone.

Two of three must pass, and Gate 2 must be one of them. If zero pass, the plan says to publish it as research rather than pretend.

What a certificate promises - and what it does not

This distinction is the product's integrity, so it is worth stating precisely. A certificate says: these verdicts reproduce when you re-run the published procedure on matching hardware. It does not say the numbers come out identical bit for bit - that is not achievable on a GPU and claiming it would be dishonest. It binds tightly on machines matching the recorded chip generation and toolchain, and is advisory elsewhere until we can prove more.

The one thing waiting on you

A quiet machine, for about an hour.

Every speed claim is stuck at "directional" until one clean measurement run exists, and that run cannot happen while apps are using the GPU. The run is already armed and will start itself: plug in power, quit everything (Terminal and VS Code included - the run survives them), kill the runaway Chrome crash-handler process if it persists, and walk away. Overnight works.

The five rules that keep the numbers honest

  1. Every method change needs a measurement behind it, written down with the result that forced it - including results that killed an idea.
  2. Predict before you measure. The next improvement is written down with its kill-criterion before the experiment runs, so a bad result cannot be reinterpreted afterwards.
  3. Grow the bug list faster than the tests adapt. Our scores stay meaningful only while the fault population outpaces our own tuning.
  4. Any 100% claim needs exact counts, never a rounded percentage.
  5. Excluding a bug as "undetectable" requires a stated proof of why no test could ever see it. Seven of the 65 are excluded that way, each with a reason on record.

Glossary

Kernel

A small program that runs on the GPU. AI models spend nearly all their time inside a handful of them.

Quantization

Compressing a model's numbers so it fits in memory - storing each in 4 bits instead of 16. Standard practice for running models locally.

Tolerance / oracle

The rule deciding whether a difference from the reference answer counts as a bug. Ours is computed per test case, not fixed.

Branch / merge

A branch is a private line of work; merging folds it into the shared trunk. Nothing merges without your approval.

Roofline

The physical ceiling for a piece of work on a given machine. Speed claims are meaningless without it.

Binding vs directional

Binding: measured under certified-quiet conditions, publishable. Directional: reproduced but not yet certified.
